Type-Safe Event Emitters in TypeScript

July 20, 2026

Node's EventEmitter is stringly typed. You emit 'data' with a buffer and listen for 'dat' with a callback expecting a string, and TypeScript won't say a word. This is fine for small scripts but becomes a real source of bugs in larger systems where events are the primary communication channel between components.

Here's a pattern I use to make event emitters fully type-safe.

The problem

Consider a monitoring system (like Pulse) where a checker emits events:

checker.emit('check:complete', { status: 200, responseTime: 45 });
checker.emit('check:failed', { error: 'ETIMEDOUT' });
checker.emit('incident:opened', { monitorId: 'abc', startedAt: new Date() });

With a plain EventEmitter, nothing stops you from emitting 'check:complet' (typo) or passing { statusCode: 200 } (wrong property name). The listener on the other end silently receives undefined fields.

The solution: mapped types over an event map

Define your events as a type map — event name to payload type:

type CheckerEvents = {
  'check:complete': { status: number; responseTime: number };
  'check:failed': { error: string; code?: string };
  'incident:opened': { monitorId: string; startedAt: Date };
  'incident:resolved': { monitorId: string; duration: number };
};

Then build a typed emitter interface using mapped types:

interface TypedEmitter<Events extends Record<string, unknown>> {
  on<K extends keyof Events>(
    event: K,
    listener: (payload: Events[K]) => void
  ): this;

  emit<K extends keyof Events>(
    event: K,
    payload: Events[K]
  ): boolean;

  off<K extends keyof Events>(
    event: K,
    listener: (payload: Events[K]) => void
  ): this;
}

Now create your class:

import { EventEmitter } from 'events';

class Checker extends (EventEmitter as {
  new (): TypedEmitter<CheckerEvents>
}) {
  async runCheck(url: string) {
    try {
      const start = Date.now();
      const res = await fetch(url);
      this.emit('check:complete', {
        status: res.status,
        responseTime: Date.now() - start,
      });
    } catch (err) {
      this.emit('check:failed', {
        error: (err as Error).message,
      });
    }
  }
}

What you get

With this pattern:

  • checker.emit('check:complet', ...) — compile error, 'check:complet' is not a key of CheckerEvents
  • checker.emit('check:complete', { statusCode: 200 }) — compile error, statusCode doesn't exist on the payload type
  • checker.on('check:complete', (payload) => { ... }) — payload is inferred as { status: number; responseTime: number }

Autocomplete works everywhere. Rename an event in the type map and every emit/listener that references it lights up red.

A reusable generic version

You can extract the casting into a helper:

function createTypedEmitter<
  Events extends Record<string, unknown>
>(): TypedEmitter<Events> {
  return new EventEmitter() as TypedEmitter<Events>;
}

const checker = createTypedEmitter<CheckerEvents>();
checker.on('check:complete', (p) => {
  console.log(p.responseTime); // number, fully typed
});

Tradeoffs

The as cast is a lie — at runtime it's still a regular EventEmitter that accepts any string. The safety is purely at the type level. If you're mixing typed and untyped code (e.g., a library emits events you didn't declare), the types won't catch mismatches at the boundary.

For most application code, where you own both the emitter and the listener, this is exactly the right tradeoff: zero runtime cost, full compile-time safety.
