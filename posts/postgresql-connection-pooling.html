PostgreSQL Connection Pooling: What I Learned Building a Multi-Tenant SaaS

July 14, 2026

When I started building ShipKit, I used pg.Pool with default settings and didn't think about it. Then I started load testing — 50 concurrent analysis requests, each reading multiple files from the GitHub API and writing results to Postgres — and the server started throwing ECONNREFUSED errors. I'd exhausted the connection pool.

Here's what I learned fixing it.

The default trap

pg.Pool defaults to 10 max connections. PostgreSQL defaults to 100 max connections. On a free-tier database (Render, Supabase, Neon), you often get 20-25. Every time you call pool.query(), it checks out a connection, runs the query, and returns it. If all connections are checked out and a new query comes in, it waits. If it waits too long, it throws.

The problem isn't usually the number of connections — it's how long each one is held. A slow query or a forgotten transaction holds a connection until it completes or times out.

What actually fixed it

Three changes:

1. Set max based on your actual database limit, not a guess.

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000,
});

If your database allows 25 connections and you have one server instance, max: 20 leaves headroom for migrations, admin queries, and your ORM's internal connections. With multiple server instances, divide accordingly.

2. Never hold connections across async boundaries without a transaction.

This is the subtle one. Consider:

// BAD: holds a connection while waiting on GitHub API
const client = await pool.connect();
const repo = await github.getRepoInfo(octokit, owner, name); // 500ms+ network call
await client.query('INSERT INTO analyses ...', [repo.data]);
client.release();

That GitHub API call takes 500ms-2s. During that time, a connection is checked out and idle. Under load, this drains the pool. Fix:

// GOOD: only hold the connection for the actual query
const repo = await github.getRepoInfo(octokit, owner, name);
await pool.query('INSERT INTO analyses ...', [repo.data]);

Use pool.query() (auto-checkout/release) for single queries. Only use pool.connect() when you need a transaction.

3. Add connection pool monitoring.

setInterval(() => {
  console.log({
    total: pool.totalCount,
    idle: pool.idleCount,
    waiting: pool.waitingCount,
  });
}, 10000);

If waitingCount is consistently above 0, your pool is too small or your queries are too slow. If idleCount equals totalCount most of the time, your pool is oversized — each idle connection still consumes memory on the database server.

Transactions done right

When you do need a transaction, use a wrapper that guarantees release:

async function withTransaction(pool, fn) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}

// Usage
await withTransaction(pool, async (client) => {
  const { rows } = await client.query(
    'INSERT INTO analyses ... RETURNING id', [...]
  );
  await client.query(
    'INSERT INTO reports (analysis_id) VALUES ($1)', [rows[0].id]
  );
});

The finally block ensures the connection is returned even if the function throws. Without it, a single unhandled error permanently leaks a connection from the pool.

When to add PgBouncer

For a single-server app with under 100 concurrent users, pg.Pool is fine. When you scale to multiple server instances — say, 3 containers behind a load balancer — each running its own pool of 20, you're suddenly opening 60 connections to a database that might only allow 100. That's when you add PgBouncer in front of Postgres. It multiplexes hundreds of application connections over a smaller number of actual database connections. Render and Supabase offer this built-in.

The key insight: connection pooling is not a performance optimization. It's a resource management strategy. Get it wrong and your app works perfectly at low load and falls over the moment real traffic arrives.
