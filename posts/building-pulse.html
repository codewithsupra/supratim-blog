Building Pulse: Real-Time API Monitoring with Node.js and WebSockets

July 28, 2026

Pulse is an uptime monitoring platform I built to solve a problem I kept running into: I'd deploy a side project, forget about it, and discover weeks later that it had been down. The existing solutions were either expensive or overkill for what I needed — hit an endpoint every 30 seconds, tell me if it's down, show me the history.

The architecture

The system has three main components:

  • Monitor scheduler — a loop that fires HTTP requests at configured intervals (30s, 1m, 5m) and records response time, status code, and any errors
  • Real-time layer — Socket.io broadcasts status changes to connected dashboard clients the moment they happen, no polling
  • Incident engine — detects downtime, tracks incident duration, and triggers notifications

The backend is Express + MongoDB. I chose Mongo over Postgres here because the monitoring data is naturally document-shaped — each check is a self-contained record with variable metadata — and I wanted capped collections for automatic TTL on historical data.

Real-time updates with Socket.io

The dashboard shows live status for all monitored endpoints. When a check completes, the server emits to the relevant room:

io.to(`monitor:${monitorId}`).emit('check:complete', {
  status: response.status,
  responseTime: elapsed,
  timestamp: new Date()
});

The client subscribes when you open a monitor's detail view and unsubscribes when you navigate away. This keeps the WebSocket traffic proportional to what you're actually looking at, not the total number of monitors.

The monitoring loop

The naive approach is setInterval per monitor. This falls apart at scale — 100 monitors with 30s intervals means 100 timers, and timer drift means checks bunch up and create traffic spikes.

Instead I use a single scheduling loop that maintains a priority queue sorted by next-check time. Each tick, it pulls all monitors due for a check, fires them concurrently with Promise.allSettled, and re-inserts them with their next scheduled time:

while (queue.length && queue[0].nextCheck <= now) {
  const monitor = queue.shift();
  batch.push(checkEndpoint(monitor));
  monitor.nextCheck = now + monitor.interval;
  insertSorted(queue, monitor);
}

const results = await Promise.allSettled(batch);

This naturally distributes checks across time and handles slow responses without blocking the queue.

Incident detection

A single failed check doesn't trigger an incident — networks are flaky. Pulse uses a confirmation window: an endpoint must fail N consecutive checks before it's marked down. The default is 3, configurable per monitor.

Once confirmed down, the incident stays open until a successful check comes back. The incident record tracks:

  • Start time (first failure in the confirmation window)
  • Confirmation time (when it crossed the threshold)
  • Resolution time (first successful check after the incident)
  • Total downtime duration
  • All individual check results during the incident

Response time visualization

The dashboard shows a sparkline of response times over the last 24 hours for each monitor. I store the raw check data and compute percentiles (p50, p95, p99) on read. For the sparkline, I downsample to 5-minute buckets using the average response time in each bucket — this keeps the chart readable without losing the shape of the data.

Development experience

One thing I'm proud of: in dev mode, Pulse auto-uses an in-memory MongoDB instance via mongodb-memory-server. No Docker, no local Mongo install, just npm run dev and it works. The server detects NODE_ENV=development, spins up the in-memory instance, and connects to it. Tests use the same mechanism — each test suite gets its own ephemeral database.

What I learned

The biggest lesson was about WebSocket connection management. Early on I had a bug where navigating between pages in the SPA would subscribe to rooms without unsubscribing from the previous ones. After a few minutes of clicking around, the client was receiving duplicate events and the dashboard was flickering. The fix was straightforward — clean up subscriptions in the React effect cleanup — but it taught me to treat WebSocket lifecycle with the same care as database connections.
