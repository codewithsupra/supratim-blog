Scaling Socket.io: Lessons from Building a Real-Time Dashboard

June 30, 2026

Pulse's dashboard updates in real time — when a monitored endpoint goes down, every user watching that monitor sees the status flip to red within seconds. Building this with Socket.io was straightforward. Making it not fall over was the interesting part.

Rooms, not broadcasts

The first version broadcast every check result to every connected client. With 10 users monitoring 50 endpoints each at 30-second intervals, that's 500 events per 30 seconds sent to every client — even if they're only looking at one monitor.

The fix is rooms. Each monitor gets a room. Clients join the room when they open the detail view and leave when they navigate away:

// Server
io.on('connection', (socket) => {
  socket.on('monitor:subscribe', (monitorId) => {
    socket.join(`monitor:${monitorId}`);
  });

  socket.on('monitor:unsubscribe', (monitorId) => {
    socket.leave(`monitor:${monitorId}`);
  });
});

// When a check completes, only notify watchers
io.to(`monitor:${monitorId}`).emit('check:result', data);

Now each client only receives events for monitors they're actively viewing. Traffic dropped by ~95%.

Reconnection strategy

Socket.io has built-in reconnection, but the defaults are aggressive — exponential backoff starting at 1 second, which means a client that loses connection hammers the server with reconnect attempts. On a server restart with 100 connected clients, you get a thundering herd.

I added jitter:

const socket = io(serverUrl, {
  reconnectionDelay: 1000,
  reconnectionDelayMax: 30000,
  randomizationFactor: 0.5,
});

The randomizationFactor adds up to 50% random variance to each delay. Instead of 100 clients all reconnecting at exactly 1s, 2s, 4s, they spread across 0.5-1.5s, 1-3s, 2-6s. The server recovers gracefully.

State synchronization on reconnect

When a client reconnects, it missed events. The dashboard might show "Up" when the endpoint has been down for 30 seconds. Socket.io doesn't replay missed events — it's not a message queue.

The solution is a state sync on reconnect:

socket.on('connect', () => {
  // Re-subscribe to rooms
  activeMonitors.forEach((id) => {
    socket.emit('monitor:subscribe', id);
  });

  // Fetch current state via REST
  activeMonitors.forEach((id) => {
    fetch(`/api/monitors/${id}/status`)
      .then((res) => res.json())
      .then((status) => updateUI(id, status));
  });
});

The REST call fetches the ground truth. From there, the socket picks up live updates. This dual approach — REST for state, WebSocket for deltas — is a pattern I use everywhere now.

The silent memory leak

Socket.io listeners are EventEmitter listeners. If you add a listener in a React useEffect without cleaning it up, every re-render adds another listener. After 50 navigations, you have 50 listeners for the same event, each updating state and triggering re-renders that add more listeners.

// The leak
useEffect(() => {
  socket.on('check:result', handleResult);
}, []); // no cleanup

// The fix
useEffect(() => {
  socket.on('check:result', handleResult);
  return () => {
    socket.off('check:result', handleResult);
  };
}, []);

This is basic React cleanup, but with WebSockets the symptoms are subtle — the app works, it just gets progressively slower and the dashboard flickers as duplicate handlers fight over state.

Multi-server: the Redis adapter

A single Socket.io server holds all connection state in memory. If you scale to two servers behind a load balancer, a client connected to server A won't receive events emitted from server B.

The @socket.io/redis-adapter solves this. Both servers subscribe to a shared Redis pub/sub channel. When server A emits to a room, Redis broadcasts it to server B, which forwards it to its local clients in that room:

import { createAdapter } from '@socket.io/redis-adapter';
import { createClient } from 'redis';

const pubClient = createClient({ url: redisUrl });
const subClient = pubClient.duplicate();
await Promise.all([pubClient.connect(), subClient.connect()]);

io.adapter(createAdapter(pubClient, subClient));

Three lines of setup and your Socket.io deployment scales horizontally. The tradeoff is a Redis dependency and ~1-5ms of additional latency per event (the pub/sub hop). For a monitoring dashboard where updates happen every 30 seconds, that's invisible.

The takeaway

WebSockets are easy to add and hard to operate. The initial implementation — io.emit('event', data) — takes 10 minutes. The reconnection strategy, state sync, memory leak prevention, and multi-server coordination take 10 hours. Budget accordingly.
