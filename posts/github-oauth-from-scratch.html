Implementing GitHub OAuth from Scratch (No Passport)

June 22, 2026

Every tutorial I found for GitHub OAuth in Node.js used Passport. Passport is fine, but it's a lot of abstraction for what is fundamentally three HTTP requests. For ShipKit, I implemented the OAuth 2.0 flow manually. It's ~60 lines of code and I understand every one of them.

The flow

OAuth 2.0 authorization code flow has three steps:

  1. Redirect the user to GitHub's authorization page
  2. GitHub redirects back to your app with a code
  3. Your server exchanges that code for an access_token

That's it. Everything else is plumbing.

Step 1: The redirect

router.get('/github', (req, res) => {
  const params = new URLSearchParams({
    client_id: config.github.clientId,
    redirect_uri: `${config.serverUrl}/api/auth/github/callback`,
    scope: 'repo read:user user:email',
  });
  res.redirect(
    `https://github.com/login/oauth/authorize?${params}`
  );
});

The scope parameter controls what your app can access. repo gives read access to repositories (needed for code analysis). read:user and user:email give you the user's profile and email. Request the minimum scopes you need — users see this list and will bounce if it looks greedy.

Step 2: The callback

GitHub redirects to your callback URL with a code query parameter. Exchange it for an access token:

router.get('/github/callback', async (req, res) => {
  const { code } = req.query;
  if (!code) return res.status(400).send('Missing code');

  // Exchange code for access token
  const tokenRes = await fetch(
    'https://github.com/login/oauth/access_token',
    {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        Accept: 'application/json',
      },
      body: JSON.stringify({
        client_id: config.github.clientId,
        client_secret: config.github.clientSecret,
        code,
      }),
    }
  );
  const { access_token } = await tokenRes.json();

The Accept: application/json header is important — without it, GitHub returns the token as a URL-encoded string instead of JSON.

Step 3: Fetch the user

With the access token, fetch the user's profile and email:

  const userRes = await fetch('https://api.github.com/user', {
    headers: { Authorization: `Bearer ${access_token}` },
  });
  const githubUser = await userRes.json();

  // Email might be private — fetch from the emails endpoint
  const emailRes = await fetch('https://api.github.com/user/emails', {
    headers: { Authorization: `Bearer ${access_token}` },
  });
  const emails = await emailRes.json();
  const primaryEmail = emails.find((e) => e.primary)?.email;

The /user endpoint returns the public profile, but the email field is often null if the user has set their email to private. The /user/emails endpoint returns all verified emails with a primary flag. You need the user:email scope for this.

Upsert and JWT

Now upsert the user in your database and create a session token:

  const user = await db.query(
    `INSERT INTO users (github_id, username, email, avatar_url, access_token)
     VALUES ($1, $2, $3, $4, $5)
     ON CONFLICT (github_id)
     DO UPDATE SET username = $2, email = $3, avatar_url = $4, access_token = $5
     RETURNING id, username, email, avatar_url`,
    [githubUser.id, githubUser.login, primaryEmail,
     githubUser.avatar_url, access_token]
  );

  const token = jwt.sign(
    { userId: user.rows[0].id },
    config.jwtSecret,
    { expiresIn: '7d' }
  );

  res.redirect(`${config.clientUrl}/dashboard?token=${token}`);
});

The ON CONFLICT clause handles returning users — if the github_id already exists, it updates their profile instead of throwing a duplicate key error. The JWT is passed to the client via a query parameter in the redirect. The client extracts it and stores it in memory (not localStorage — see below).

Where to store the JWT

Three options, each with tradeoffs:

  • localStorage — persists across tabs and page reloads, but vulnerable to XSS. Any JavaScript running on your page can read it.
  • httpOnly cookie — immune to XSS (JavaScript can't access it), but you need CSRF protection and it's sent with every request to your domain.
  • In-memory variable — immune to both XSS and CSRF, but lost on page refresh. The user has to re-authenticate.

For ShipKit, I use in-memory storage with a short-lived JWT. If the page refreshes, the user re-authenticates through GitHub — and since they've already authorized the app, GitHub redirects back immediately without showing the authorization screen. The UX is a brief flash; the security posture is clean.

Why not Passport

Passport is 600+ lines of code with a strategy pattern, session serialization, and middleware chaining. For a single OAuth provider, that's a lot of abstraction over three fetch calls. The manual implementation is easier to debug (no middleware chain to trace), easier to understand (no serialize/deserialize hooks), and has zero dependencies beyond what you already have.

If you're integrating 5 OAuth providers with session management across multiple auth strategies, use Passport. If you're doing GitHub-only OAuth for a side project, the manual approach is ~60 lines and you'll actually understand what happens when something breaks.
