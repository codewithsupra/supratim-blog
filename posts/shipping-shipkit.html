ShipKit: From GitHub Link to Deploy-Ready in Minutes

July 31, 2026

I built ShipKit because I was tired of the same manual checklist every time I wanted to deploy a side project: scan for leaked secrets, check if there's a Dockerfile, figure out whether Vercel or Render is the right fit, make sure dependencies aren't ancient. So I automated all of it.

What it does

You connect your GitHub account, pick a repo, and ShipKit runs five analysis passes over your codebase:

  1. Framework detection — reads file signatures (next.config.js, manage.py, go.mod) and package.json dependencies to identify your stack
  2. Security scanning — regex-based detection of AWS keys, private keys, GitHub tokens, hardcoded credentials, committed .env files
  3. Best practices — checks for Dockerfile, CI/CD config, test files, linter config, README, lock files, LICENSE
  4. Dependency analysis — flags known-vulnerable packages (event-stream, ua-parser-js), deprecated ones (request, moment), and test libs in production deps
  5. Deploy recommendation — based on your framework, database usage, WebSocket needs, and whether you have a Dockerfile, it recommends Vercel, Render, Railway, Fly.io, or AWS with a reason

You get a score out of 100, a list of findings sorted by severity, and a PDF action report you can download or have emailed to you.

Architecture

The stack is intentionally simple:

  • Backend: Node.js + Express + PostgreSQL. The analysis engine uses @octokit/rest to fetch the repo tree and read files directly from the GitHub API — no cloning needed.
  • Frontend: React + Vite. The dashboard shows your repos in a grid; click "Analyze" and the results page renders with an animated SVG score ring.
  • Auth: GitHub OAuth 2.0 implemented from scratch — no Passport. The callback exchanges the code for an access token, fetches user info, upserts into Postgres, and redirects with a JWT.
  • PDF generation: PDFKit with a styled header, color-coded score circle, severity badges for findings, and a deployment recommendation card.

The scoring system

Score starts at 100 and deducts by severity:

critical  → -20 points
high      → -12 points
medium    →  -6 points
low       →  -3 points

A repo with two critical findings and three medium ones scores 100 - 40 - 18 = 42. The color coding maps to familiar ranges: green above 80, yellow 60-80, orange 40-60, red below 40.

Security scanning approach

The security scanner uses targeted regex patterns rather than trying to be comprehensive. It catches the most common leaks I've seen in real repos:

// AWS access key pattern
/AKIA[0-9A-Z]{16}/

// GitHub token patterns
/ghp_[a-zA-Z0-9]{36}/
/github_pat_[a-zA-Z0-9]{22}_[a-zA-Z0-9]{59}/

It also checks structural issues: is .env committed? Is there a .gitignore? Is there a .env.example for onboarding?

How deploy recommendations work

The recommender builds a profile of the repo — has database, has WebSockets, is static, is SSR, has Dockerfile — then matches against platform strengths:

  • Next.js without a database → Vercel
  • Static site (no server files, no API routes) → Netlify
  • Has a Dockerfile + database → Render
  • WebSockets or long-running processes → Fly.io
  • Complex infra needs → AWS

Each recommendation includes the reasoning, platform strengths, and two alternatives so you're not locked into one opinion.

What's next

Phase 2 is auto-deployment: after analysis, ShipKit generates the deployment config (render.yaml, vercel.json, fly.toml) and deploys directly. The analysis engine becomes the first step in a fully automated ship pipeline. That's the vision — from GitHub link to live URL in minutes, not hours.
